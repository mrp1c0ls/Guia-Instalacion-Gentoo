¿Qué se logra en este capítulo?

Hasta el capítulo 24 el sistema es un esqueleto: tiene archivos base pero no sabe nada de software disponible. Aquí se le enseña a Portage (el gestor de paquetes de Gentoo) qué paquetes existen, qué perfil de configuración usar, y qué opciones de compilación aplicar por defecto. Es la puesta a punto antes de instalar kernel, bootloader y el resto del sistema.

Contexto importante: Gentoo es una distribución basada en código fuente. Cada emerge normalmente descarga el código fuente de un paquete y lo compila en tu propia máquina, no instala un binario prehecho (salvo que actives paquetes binarios, ver más abajo). Por eso toda esta configuración de Portage importa tanto: define cómo se comporta cada compilación, para siempre, no solo en la instalación inicial.

1. Descargar el repositorio ebuild bajo riesgo

Un ebuild es la "receta" que le dice a Portage cómo compilar e instalar un paquete. El repositorio ebuild es la colección completa de esas recetas — sin él, emerge no sabe que un paquete existe. 

root # emerge-webrsync

Para qué sirve: descarga un snapshot diario del repositorio vía HTTP/FTP (funciona incluso detrás de firewalls restrictivos) y lo coloca en /var/db/repos/gentoo/.

Opcional — Actualizar el repositorio a la última hora (no solo al día) 
root # emerge --sync

Para qué sirve: usa el protocolo rsync para traer cambios más recientes (hasta ~1 hora de antigüedad) en vez del snapshot diario de emerge-webrsync. Es totalmente opcional en la instalación inicial.

root # emerge --sync --quiet

Para qué sirve: igual que arriba, pero silenciando la salida — recomendado en terminales lentas (framebuffer, consola serial).

2. Noticias de Gentoo

Al sincronizar, Portage puede avisar de news items: comunicados oficiales sobre cambios importantes (por ejemplo, migraciones de perfil que requieren pasos manuales). 

root # eselect news list
root # eselect news read

Para qué sirve: eselect es la herramienta genérica de Gentoo para gestionar distintos aspectos del sistema mediante "módulos" (aquí, el módulo news). list muestra los comunicados pendientes, read los muestra completos.

3. Elegir el perfil del sistema impacto medio

Un perfil es una plantilla mantenida por los desarrolladores de Gentoo que define valores por defecto de USE, CFLAGS y otras variables, además de fijar un rango de versiones de paquetes compatibles entre sí. 

root # eselect profile list

Para qué sirve: muestra los perfiles disponibles para tu arquitectura, con un número al lado de cada uno.

root # eselect profile set 2

Para qué sirve: selecciona el perfil número 2 de la lista anterior como base de configuración del sistema.

Advertencia del propio handbook: al elegir el perfil inicial, usa la misma versión que trae tu stage file (por ejemplo, 23.0). Cambiar de versión de perfil más adelante no es trivial — siempre viene anunciado por un news item con instrucciones de migración.

Los perfiles y los sistemas init (OpenRC, systemd y más)

Algo que no siempre es obvio al mirar la lista de perfiles: el nombre del perfil determina qué sistema init (el proceso que arranca todo lo demás al encender la máquina) usará tu instalación. Gentoo es de las pocas distros que te deja elegir esto desde el principio.

Sistema initCómo se ve en el perfilNotas
OpenRC default/linux/amd64/23.0 (sin "systemd" en el nombre) El init tradicional de Gentoo. Basado en scripts shell y dependencias declaradas simples. Servicios se gestionan con rc-update / rc-service. Es la configuración usada en este proyecto.
systemd default/linux/amd64/23.0/systemd Init más extendido en otras distros (Fedora, Arch, Debian). Gestiona servicios, logs (journald) y más como un conjunto integrado. Servicios con systemctl enable/start.
Otros (no cubiertos por perfiles oficiales) — Gentoo también permite runit o s6 vía overlays/paquetes de la comunidad, aunque no tienen un perfil oficial dedicado como OpenRC/systemd — requieren configuración manual adicional.
Nota: el capítulo 26 del handbook (opcional) cubre systemd en detalle. Si tu perfil no incluye "systemd" en el nombre, tu sistema queda en OpenRC — que es el caso de esta instalación.
Sub-perfiles no-multilib (solo 64-bit puro) 
root # eselect profile list
...
 [5] default/linux/amd64/23.0/no-multilib
root # eselect profile set 5

Para qué sirve: elimina la capacidad de correr binarios de 32-bit en un sistema 64-bit. Útil si nunca vas a necesitar compatibilidad con software antiguo de 32-bit.

4. Paquetes binarios (opcional) ahorra tiempo

Por defecto Portage compila todo desde código fuente. Si prefieres velocidad sobre optimización a medida, puedes usar binarios ya compilados por Gentoo (el "binhost oficial"). 

FEATURES="${FEATURES} getbinpkg"
FEATURES="${FEATURES} binpkg-request-signature"

Para qué sirve: le dice a Portage que, al pedir un paquete, primero pregunte al binhost si existe un binario compatible, y solo compile localmente si no lo encuentra. binpkg-request-signature exige que ese binario venga firmado criptográficamente.

root # getuto

Para qué sirve: configura el llavero (keyring) necesario para verificar esas firmas antes de instalar cualquier binario.

5. La variable USE — a fondo alto impacto

Las USE flags son el mecanismo con el que decides qué funcionalidades opcionales se compilan dentro de cada paquete. A diferencia de distros binarias (que suelen incluir "todo por si acaso"), Gentoo te deja decidir tú.

Sintaxis básica 
USE="ssl -X gnome gtk -kde -qt5"
  • ssl → compila con soporte para cifrado SSL/TLS
  • -X → el signo menos significa "sin esto" (sin servidor gráfico X11)
  • gnome gtk -kde -qt5 → favorece el ecosistema GNOME/GTK, descarta KDE/Qt

¿Por qué importan? Ejemplos concretos

SituaciónSin ajustar la flagCon la flag ajustada
Servidor sin monitor Se compilan decenas de paquetes con soporte X11/GUI innecesario USE="-X" ahorra tiempo de compilación y espacio en disco
Sistema de audio Un reproductor podría traer PulseAudio aunque tu sistema use ALSA puro alsa -pulseaudio evita instalar un demonio de audio que nunca arrancará
Seguridad / superficie de ataque Más código compilado = más código que podría tener vulnerabilidades sin usarse nunca Desactivar soporte no usado (ej. -ftp -telnet en un cliente) reduce esa superficie
Un solo paquete necesita algo distinto al resto Cambiar el USE global afectaría a todo el sistema package.use/ permite la excepción solo para ese paquete
Importante: nunca instalas "sin" USE flags — siempre hay un conjunto activo (el del perfil, más lo que agregues en make.conf). La pregunta nunca es "¿uso USE flags o no?", sino "¿acepto las que trae el perfil por defecto, o las personalizo?".
¿Dónde se configuran? Global vs. por paquete

Global — afecta a todos los paquetes que reconozcan esa flag:

# /etc/portage/make.conf
USE="X gtk -kde alsa -pulseaudio"

Por paquete — sobreescribe la regla global, solo para ese paquete:

# /etc/portage/package.use/mpv
media-video/mpv pulseaudio -alsa

Para qué sirve package.use/: evita que make.conf crezca sin control. Es un directorio, no un archivo único — Portage lee todo lo que haya dentro, sin importar cómo lo organices (por paquete, por tema, etc.). Sigue la lógica de "regla general en make.conf, excepciones puntuales en package.use/".

Advertencia del handbook: nunca uses USE="-*" (desactivar todo). Los desarrolladores de cada ebuild eligen valores por defecto para evitar conflictos y errores — desactivarlo todo puede romper el sistema de formas inesperadas.

USE flags de hardware: CPU_FLAGS_X86 y VIDEO_CARDS

Son dos variables especiales, ligadas a tu hardware físico, independientes entre sí.

CPU_FLAGS_X86VIDEO_CARDS
Hardware que describeTu procesador (CPU)Tu tarjeta gráfica (GPU)
¿Es obligatorio configurarlo?No, pero no tiene desventaja hacerloPrácticamente sí, si hay GPU dedicada o interfaz gráfica
Qué controlaRutas de código especiales escritas a mano por cada paquete (cifrado, codecs de video) que aprovechan instrucciones concretas del CPU (AVX2, AES-NI, SSE4.2...)Qué driver de GPU compilar en Xorg/Mesa/el kernel
Dónde se notaSoftware de cómputo pesado: cifrado (OpenSSL), codificación de video (ffmpeg, x264), gráficos (Mesa)Cualquier cosa que dibuje en pantalla o use aceleración de GPU
No confundir con -march=native: CFLAGS="-march=native" le dice al compilador que optimice automáticamente el código para tu CPU. CPU_FLAGS_X86 activa rutas de código manuales escritas por los desarrolladores del paquete — son mecanismos distintos y complementarios, no sustitutos entre sí. 
root # emerge --ask --oneshot app-portage/cpuid2cpuflags
root # cpuid2cpuflags
root # echo "*/* $(cpuid2cpuflags)" > /etc/portage/package.use/00cpu-flags

Para qué sirve: cpuid2cpuflags detecta automáticamente qué instrucciones soporta tu CPU real (no hay que adivinarlo a mano) y genera el archivo package.use correspondiente, aplicado a todo paquete (*/*) que use esa flag.

# /etc/portage/package.use/00video_cards
*/* VIDEO_CARDS: -* amdgpu radeonsi

Para qué sirve: primero desactiva (-*) los drivers genéricos que trae el perfil por defecto, luego activa solo el tuyo — evita compilar soporte para tarjetas gráficas que no tienes.

6. ACCEPT_LICENSE

Controla qué licencias de software tu sistema tiene permitido instalar. Por defecto, solo se permite software agrupado en @FREE (libre, según la definición de la FSF/OSI). 

user $ portageq envvar ACCEPT_LICENSE
@FREE

Para qué sirve: consulta el valor actual configurado en el sistema.

# /etc/portage/make.conf
ACCEPT_LICENSE="-* @FREE @BINARY-REDISTRIBUTABLE"

Para qué sirve: amplía lo permitido — aquí se agregan también licencias que permiten redistribuir binarios, aunque no sean 100% libres.

También se puede ajustar por paquete en /etc/portage/package.license/, igual que con package.use/.

7. El conjunto @world

Es la lista de paquetes que instalaste explícitamente — no las dependencias que se jalaron automáticamente. Vive en /var/lib/portage/world. 

root # emerge --ask --verbose --update --deep --changed-use @world

Para qué sirve: actualiza todo lo que pediste explícitamente (y sus dependencias), recompilando lo necesario si cambiaron USE flags o el perfil.

root # emerge --ask --pretend --depclean
root # emerge --ask --depclean

Para qué sirve: detecta y elimina paquetes que ya nadie necesita (ni tú los pediste, ni son dependencia de algo que sí pediste). --pretend primero simula el resultado sin borrar nada — conviene revisarlo antes del depclean real.

Comparación con NixOS: @world se parece a environment.systemPackages, pero no es declarativo ni reproducible — es más un registro que Portage va actualizando según los comandos emerge que ejecutes, no un archivo que edites a mano para reconstruir el sistema desde cero.

Resumen del flujo mínimo

1
emerge-webrsync — obtener el catálogo de paquetes disponibles
2
eselect profile list / set N — elegir perfil (define también OpenRC vs. systemd)
3
(Opcional) ajustar USE, CPU_FLAGS_X86, VIDEO_CARDS y ACCEPT_LICENSE
4
(Opcional) emerge --ask --verbose --update --deep --changed-use @world
