Cap. 45–46 · Bootloaders alternativos

systemd-boot y EFI Stub — la instalación de referencia usa GRUB, así que estos capítulos son contexto, no ejecución.

No aplica a tu instalación (usas GRUB) OpenRC systemd

¿Por qué existen 3 formas de arrancar?

Un firmware UEFI ya sabe ejecutar un archivo .efi directamente — técnicamente no necesita un "bootloader". Las tres opciones del Handbook son distintos niveles de comodidad sobre esa base:

GRUBsystemd-bootEFI Stub
Qué haceBootloader completo con menú, detección automática, scriptingChainloader delgado, solo lee entradas de textoEl kernel es el ejecutable EFI; no hay intermediario
Detecta kernels soloSí (grub-mkconfig)Sí (convención de archivos)No — se registra cada uno a mano
OpenRC✅✅✅
systemd✅✅ (su entorno natural)✅
Complejidad configuraciónAltaBajaMedia (todo manual)
Para qué sirve saber esto Si en el futuro migras a un equipo distinto, cambias a systemd, o simplemente el firmware de una placa da problemas con GRUB, tener claro el panorama te permite elegir la alternativa correcta sin partir de cero.

45 · systemd-boot

Es un cargador minimalista: no tiene lenguaje de configuración propio, solo lee archivos .conf por cada entrada de arranque. Funciona igual de bien en OpenRC que en systemd, porque solo necesita el binario y la herramienta bootctl — no arrastra el resto del ecosistema systemd (PID 1, journald, etc.).

45.1 Emerge — instalar el paquete correcto

Dónde se configura /etc/portage/package.use/systemd-boot 
FILE /etc/portage/package.use/systemd-boot
sys-apps/systemd boot          # sistemas con systemd
sys-apps/systemd-utils boot    # sistemas con OpenRC
root # emerge --ask sys-apps/systemd        # systemd
root # emerge --ask sys-apps/systemd-utils  # OpenRC

El USE flag boot es el interruptor que activa el componente de instalación/gestión de systemd-boot dentro de ese paquete. Sin él, el paquete se compila sin esa funcionalidad.

45.2 Instalación — un solo comando

root # bootctl install
Para qué sirve Copia el binario systemd-bootx64.efi a la ESP (tu /efi) y lo registra en el firmware. No existe un paso equivalente a grub-mkconfig: las entradas de arranque las genera installkernel automáticamente cada vez que instalas un kernel, no bootctl.
Riesgo: bajo, pero con condición La ESP debe estar montada (en /efi) antes de correr el comando, o systemd-boot no tendrá dónde escribir.
Verificar que la entrada de arranque quedó registrada 
root # bootctl list

Muestra las entradas detectadas. Si el kernel line de arranque parece incorrecto (por ejemplo, usa parámetros del live CD), crea manualmente /etc/kernel/cmdline con la línea correcta y reinstala el kernel.

45.3 Secure Boot (opcional)

Dos caminos según qué acepte tu firmware:

EscenarioQué hacer
El firmware acepta certificados propiosActivar USE flag secureboot globalmente → Portage firma el ejecutable automáticamente, bootctl install instala la versión ya firmada.
El firmware solo confía en Microsoft (caso más común)Usar shim como intermediario pre-firmado.
Configurar shim paso a paso 
root # emerge --ask sys-boot/shim sys-boot/mokutil sys-boot/efibootmgr
root # bootctl install --no-variables
root # cp /usr/share/shim/BOOTX64.EFI /efi/EFI/systemd/shimx64.efi
root # cp /usr/share/shim/mmx64.efi /efi/EFI/systemd/mmx64.efi

Shim ya está firmado por Microsoft, así que casi cualquier placa lo acepta por defecto. Shim, a su vez, confía en tu certificado propio — hay que "presentárselo":

root # openssl x509 -in /path/kernel_key.pem -inform PEM -out /path/kernel_key.der -outform DER
root # mokutil --import /path/kernel_key.der

Registrar shim con el firmware (reemplaza boot-disk y boot-partition-id):

root # efibootmgr --create --disk /dev/boot-disk --part boot-partition-id \
  --loader '\EFI\systemd\shimx64.efi' \
  --label 'Systemd-boot via Shim' \
  --unicode '\EFI\systemd\systemd-bootx64.efi'
Nota La importación no se completa hasta reiniciar. Al arrancar aparecerá MokManager pidiendo la contraseña que definiste en mokutil --import — ahí confirmas que confías en esa llave, y luego ya puedes activar Secure Boot en el menú UEFI.

46 · EFI Stub — arranque sin bootloader

El enfoque minimalista: el kernel compilado es el ejecutable EFI. No hay menú, no hay configuración intermedia — cada entrada se registra directamente en el firmware.

firmware UEFI → lee entrada NVRAM (efibootmgr) → ejecuta bzImage.efi directamente

Preparar el USE flag y el kernel

Dónde se configura /etc/portage/package.accept_keywords/installkernel y /etc/portage/package.use/installkernel 
FILE /etc/portage/package.accept_keywords/installkernel
sys-kernel/installkernel **
FILE /etc/portage/package.use/installkernel
sys-kernel/installkernel efistub
Por qué hay que aceptar keywords "testing" EFI Stub no está garantizado en todas las implementaciones UEFI (varían mucho entre fabricantes), por eso el flag efistub está enmascarado como inestable — Gentoo te obliga a aceptarlo explícitamente. 
root # emerge --ask sys-kernel/installkernel
root # mkdir -p /efi/EFI/Gentoo
root # emerge --ask --config sys-kernel/gentoo-kernel{,-bin}   # kernels de distro
root # make install                                             # kernel manual
Alternativa: copiar el kernel a mano (sin installkernel) 
root # mkdir -p /efi/EFI/Gentoo
root # cp /boot/vmlinuz-* /efi/EFI/Gentoo/bzImage.efi

Registrar la entrada de arranque

root # emerge --ask sys-boot/efibootmgr
root # efibootmgr --create --disk /dev/sda --part 1 --label "gentoo" \
  --loader "\EFI\Gentoo\bzImage.efi"
Para qué sirve efibootmgr No es el bootloader en sí — es la herramienta que edita las variables EFI (la lista de entradas de arranque que vive en el firmware, tipo NVRAM). Con GRUB o systemd-boot esto lo hacen ellos solos; aquí lo haces tú manualmente por cada kernel.

Si usas initramfs, se agrega como parámetro extra en la misma entrada:

root # efibootmgr --create --disk /dev/sda --part 1 --label "gentoo" \
  --loader "\EFI\Gentoo\bzImage.efi" \
  --unicode "initrd=\EFI\Gentoo\initramfs.img"
Nota importante El separador de rutas en definiciones UEFI es \ (backslash), no / — es una convención heredada de Windows que el estándar UEFI mantuvo.

46.1 Unified Kernel Image (UKI)

Un UKI empaqueta en un solo archivo .efi: kernel + initramfs + línea de comandos de arranque. Es la forma más "limpia" de usar EFI Stub, porque reduces todo a un único ejecutable en vez de gestionar kernel e initramfs por separado.

InitPaquete/flag necesario
systemdsys-apps/systemd boot
OpenRCsys-apps/systemd-utils boot kernel-install

Requiere un "stub loader" — actualmente solo existe systemd-stub, por eso aparece systemd/systemd-utils aunque estés en OpenRC.

Generar el UKI con dracut o ukify 
FILE /etc/portage/package.use/uki (con dracut)
sys-kernel/installkernel dracut uki
FILE /etc/portage/package.use/uki (con ukify)
sys-kernel/installkernel dracut ukify uki

dracut puede generar initramfs y UKI. ukify solo genera el UKI final — el initramfs lo sigue haciendo dracut por detrás.

root # emerge --ask sys-kernel/installkernel

Entrada de arranque para el UKI ya generado (queda en /efi/EFI/Linux/):

root # efibootmgr --create --disk /dev/sda --part 1 --label "gentoo" \
  --loader "\EFI\Linux\gentoox.y.z.efi"
Con Secure Boot activo El cmdline queda "grabado" dentro del UKI firmado. El firmware ignora cualquier parámetro pasado desde fuera — es intencional, para que nadie altere el arranque sin volver a firmar el archivo.

En tu instalación (GRUB + dracut)

No ejecutas nada de este capítulo. El único punto de contacto real con tu setup: dracut también genera tu initramfs para GRUB — es la misma herramienta, solo que aquí se usa de forma "fusionada" (UKI) en vez de como archivo separado.
